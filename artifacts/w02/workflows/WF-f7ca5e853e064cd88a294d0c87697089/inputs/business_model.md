# 青禾会员运营业务模型

版本：v0.2-final，2026-11-03。W02 提交定稿，AI 协助整理。业务定义、规则与适用条件沿用已确认的 v0.2；版本沿革、核查取舍与 Agent 对照证据见访谈与核查记录。本模型是基于课程模拟访谈形成的业务认识，不代表公司制度、已实现的执行系统或已交付的数据能力。

## 1. 问题与范围

本模型解释三件事：会员建议怎样被判断是否纳入本次运营任务；哪些信息构成门店接手活动的前提；信息缺失、范围变化或建议不匹配时，三位角色怎样协作。业务主线是「有依据、可审核的人群与动作建议 → 运营判断纳入 → 门店在执行前拿到足够信息并确认执行条件」，目标是减少运营的二次整理，但该减负效果尚无任何量化依据。

依据是七份课程模拟访谈（小林三场、陈姐两场、老周两场）。没有客户系统数据、真实会员名单、实际活动说明或执行记录，也没有耗时基线、验收条件和效果指标。因此本模型只能支持「建议该怎样核对与交接」这类判断，不能据此计算真实人群、证明业务效果、证明权限已取得或执行任何营销动作。

小林希望先减轻整理名单和执行记录的负担（L3 MSG-02910）；陈姐希望减少门店接待顾客时因活动要求不清而反复找人确认（C2 MSG-02856）。这是两个岗位各自的优先诉求，本模型并列保留，不合成共同确认的项目优先级或验收指标；现有材料没有显示两人在资源或方案上互相排斥，因此也不构成已成立的业务分歧。

来源代号与完整路径见[访谈与核查记录](interview_notes.md#来源索引)；引用 L3 等代号加消息 ID 可定位原件。本轮使用的提取运行为 `artifacts/w02/runs/RUN-2a97772232df4e4c9b736feb67ba7f0b/run.json`，产出 127 条候选与 4 组机器冲突分组。运行成功与程序结构检查通过只说明提取流程完成，不代表候选语义已被验证；本轮取舍以原文与 FDE 核查理由为准，不直接继承机器标记。

## 3. 规则、条件与职责

### R1 会员建议的采用条件

小林先核对每条建议为什么圈出该会员、依据是什么，再对照本次任务的会员范围、计划动作和已有反馈，判断是否适合纳入本次任务（L3 MSG-02912、MSG-02914）。是否纳入本次任务通常由她判断；涉及线上或门店执行安排时，再找相关同事核对（L3 MSG-02920）。这是她对自己工作方式和本次任务范围的自述，不是公司统一制度；满足这些核对条件也不等于可以自动执行。她确认的范围是「是否纳入本次任务」，不扩大为对整个项目、数据权限或所有执行方案的批准。具体核对岗位、例外情形和确认留痕仍未知。

### R2 不匹配建议与自动动作边界

对与本次任务对不上的那部分建议，小林先不纳入执行，也不把它当成可执行名单，并继续对照没做完的运营任务和已有反馈、找相关同事核实不清楚的地方（L3 MSG-02932）。不能写成永久拒绝或已删除建议；也没有实际名单或执行记录证明该处理已发生。

小林表示，对不匹配建议尚未确认时不执行自动发券、联系会员或修改记录等动作；她同时明确没有授权助手自动发券、联系会员或改记录（L3 MSG-02932、MSG-02910）。因此模型同时保留「本次未授权」与「确认前不执行」两项，不能只保留时间条件，也不能反推「确认纳入后就自动获得动作授权」。该未授权也不等于永久禁止：后续是否授权、由谁批准、需什么条件仍未知。规则描述的是角色要求，没有发生真实执行或系统阻断验证。

### R3 门店接手的必要信息条件

按陈姐的判断标准，一份活动说明能否交给门店，先看它是否讲清六项：活动面向哪些会员、哪些门店参与、门店具体要做什么、大概多少工作量、现场顾客的问题由谁答、门店出的力怎么记下来（C2 MSG-02860）。缺一项或含糊，说明就不能直接下发；她要求先标出缺的、含糊的地方交运营核实（C2 MSG-02865）。只要活动可能影响门店考核，还需先澄清或调整，不能默认门店已经接受（C2 MSG-02860、MSG-02871）。

这六项是陈姐提出的必要信息条件，不等于公司批准的制度，也不等于六项齐全即可下发：信息完整不等于已获准发布，也不替代门店人员对具体执行的确认。小林认同先标缺口、不直接发门店的做法（L3 MSG-02916），但她的表述是「平时的做法」，不代表某次活动已核实有效或已见效。

### R4 运营与门店的协作与确认层级

工作量不是小林单方估算：她先把本次面向哪些会员、准备做什么写清楚，再拿这个与陈姐对接门店执行安排，门店大概要接多少工作量在对接时一起确认（L3 MSG-02924）。这与陈姐要求说明里写清「大概多少工作量」不矛盾——一项讲说明应包含什么，一项讲数值怎样形成；但实际活动中是否都这样执行、工作量怎样估算和留痕，仍需同一次活动的说明与对接记录验证。

现场答疑责任由小林在准备活动安排、与陈姐核对时一并提出确认；门店现场具体怎么安排属于门店情况，她不替门店定（L3 MSG-02926）。陈姐侧先核对活动面向哪些会员、哪些门店参与、门店具体要做什么，再向门店同事说明并确认人员和执行安排；具体执行由门店同事确认（主要确认人员怎么排、现场执行安排能否落实）（C MSG-01399、MSG-01409）。因此可表达的协作层级为：小林提出并与陈姐核对 → 陈姐核对信息、向门店说明并协同确认 → 门店人员确认具体人员和执行条件。这不是三级审批流程，也不表示陈姐对全部现场安排独自决策或兜底；具体答疑人员、岗位分工、确认载体与留痕仍未知（C MSG-01409；C2 MSG-02871）。

门店怎样记录这份工作，小林交由陈姐侧确认，自己不替门店定具体记法（L3 MSG-02928）；陈姐说具体记哪些项目、记录最后交给谁、用来做什么，她需查实际记录并向运营核实（C MSG-01403）。两者分别描述「核实接口归属」与「记录细则仍待取证」，尚不构成同一事项上的互斥主张；但这是责任边界上的待核线索，需对齐同一次活动的记录项目、填写人、接收人、用途与责任约定。陈姐侧作为核实接口，不等于她能单独制定记录规则或考核制度。

权限边界：陈姐能安排自己负责范围内的日常执行和人员配合，但认为考核规则与跨部门预算她改不了，也不替门店默认接受（C2 MSG-02871）。考核规则和预算的实际决定人未知。

### R5 业务范围与系统统计的协作

需要核查、尤其范围调整时，小林先说明或确认业务会员范围、动作与用途，并明确系统统计的范围、时间和统计说明由老周那边核对、她不替系统口径确认，两边对上后再一起看是否一致（L3 MSG-02918）。这条是小林针对访谈者对老周分工的转述作出的认可，同时包含她对自己日常职责（整理运营任务、准备活动安排、协调线上线下执行）的直接说明；不把访谈者提问本身当作业务事实。老周侧另有直接陈述：他会与她一起确认她说的会员范围，再核对系统统计用的范围、时间和统计说明，整理需要补的记录并评估技术影响（Z2 MSG-02826、MSG-02831）。

因此可表达的协作关系是：业务范围与用途由小林侧说明或确认，系统统计范围与统计说明由老周侧核对，双方比较是否一致。这不是小林代替系统口径确认，也不是老周决定业务范围；不强行规定两步的先后，也不是每项活动必经的固定审批链。老周原文明确：这些是配合核查的步骤，不代表数据已交付或人数已核实（Z2 MSG-02826）。

老周要求业务侧先给出具体问题、准备使用的数据范围、用途和需谁配合的清单，并把疑点落到具体记录或统计说明上逐项核对（Z MSG-01422、MSG-01424；Z2 MSG-02820）。安全、用途、责任不明确时，他可要求暂缓技术接入，补齐后再评估（Z2 MSG-02820）；他可安排职责内的技术核查并提出接入条件，但认为效果口径、活动费用、合同不归他定（Z2 MSG-02822）。门店执行上的解释找陈姐（Z MSG-01424）。

数据权限：老周明确本次访谈没有批准任何具体数据权限，后续安排他不掌握，不能当成已定流程（Z2 MSG-02831、MSG-02822）。这是有原文支持的授权状态说明；审批人、审批步骤、未来自动获权条件均不得补造，也不能据此推定历史数据权限状况。

### R6 范围变化与旧项目线索

需求／范围变化时，老周不会一口回绝，但要求先说明变了什么、用途是什么、核查范围动到哪一步，再判断技术上要补什么（Z2 MSG-02822）；他以「原本只核实一种会员范围、后来范围改了，已确认的取数或接入可能得重做」作为说明性风险举例，不是已核实的历史事件。

旧项目「需求一直在变」是老周的个人观察，不是项目环节清单，也不是原因结论；具体哪次变化、来自哪些沟通或材料，他需查记录核对，也不能断定变化是因为原需求没满足业务要求（Z MSG-01418、MSG-01426；Z2 MSG-02824）。这与现有背景资料《智能营销平台项目阶段结项汇报》第 2 页对需求调整的正面表述（「需求完善带动方案持续调整」）构成同一问题上的不同评价；该材料属既有背景资料，不是本轮七份访谈的提取输入。相关不同评价与取证计划见核查记录第四节 DIS-001，保留为待事件级核实的线索，不写成互斥事实、不认定返工责任，也不据此改变本期立项判断。

## 4. 候选助手能力与建模理由

候选能力包括：整理带依据的会员建议；辅助整理活动说明；标出信息缺口与不匹配之处；整理范围变更时需说明的事项。它们来自角色需求与本文设计选择，尚未实现或验证；不包含自动发券、联系会员、改记录、发布活动或批准权限。

把建议、任务、活动安排分开，是为了表达「提出候选—判断纳入—核对执行条件」的区别，避免把已有建议当执行许可。把「纳入判断」与「执行安排核对」分开，是为了不把小林的岗位确认扩大为项目或权限批准。单独表达门店参与，是为了保留不同门店的适用范围与执行确认。把核实接口与决定权限分开（陈姐侧、老周侧），是为了避免把协调职责扩大为制度制定或数据授权。会员身份不设互斥约束、久未回购不设阈值，是为了不把未知口径写死。以上是建模理由，不是客户批准的软件设计。
